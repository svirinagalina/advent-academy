# Управление пользователями

Раздел `/?view=users` доступен ADMIN. Ссылка находится рядом с курсами в кабинете
управления. Дизайн и состояния описаны в
[`USER_ADMIN_DESIGN_SPEC.md`](../../frontend/design-reference/USER_ADMIN_DESIGN_SPEC.md).
Список, карточка, история и формы используют реальные данные user-service.

Поиск работает по имени и email без минимальной длины; роль и статус выбираются
по одному. Страница содержит 20 пользователей. Поиск, фильтры, страница и вкладка
хранятся в URL; возврат из карточки сохраняет выдачу. Старые ответы отменённых
запросов не заменяют актуальную выдачу. Пустая выдача, загрузка, ошибки и повтор
поддерживаются отдельно. Темы используют существующие токены и Golos Text,
иконки — Lucide. На узком экране таблица превращается в карточки.

## Контракт API

Все административные маршруты начинаются с `/api/users/admin`, требуют bearer JWT
с ADMIN и дополнительно проверяют текущую роль и состояние администратора в БД.
BFF разрешает только перечисленные методы, проверяет Origin для записи,
использует серверную сессию и `no-store`. Административный JSON ограничен 32 KiB.

| Метод и суффикс | Запрос / назначение |
| --- | --- |
| GET | `query`, `role`, `status`, `page` от 0, `size` от 1 до 100; ответ `{items,total,page,size}` |
| POST | `{requestId,firstName,lastName,email,roles}`; создание и попытка отправки приглашения |
| GET `/{id}` | Карточка с `version`, независимыми состояниями доступа и приглашения, допустимыми действиями |
| PUT `/{id}/roles` | `{version,roles}`; замена четырёх управляемых ролей |
| POST `/{id}/block` | `{version}`; административная блокировка |
| POST `/{id}/unblock` | `{version}`; снятие административной блокировки |
| POST `/{id}/unlock` | `{version}`; снятие временной блокировки входа |
| POST `/{id}/invitation` | `{requestId}`; повтор приглашения существующему пользователю |
| GET `/{id}/history` | `page`, `size`; события с неизменяемым именем автора |

Отдельный публичный POST `/api/auth/invitations/accept` принимает
`{token,password,confirmPassword}`. Страница `/auth/accept-invitation` вызывает его
через BFF `/api/invitations` с проверкой Origin и лимитом 8 KiB. Прямой endpoint
применяет существующую квоту password-reset по IP до вычисления хеша пароля.

Имя и фамилия обязательны, максимум 50 символов после обрезки пробелов на клиенте;
API ограничивает также исходные поля. Email обязателен, максимум 255 символов,
нормализуется через trim и lower-case. Поиск регистронезависимый, `%` и `_`
интерпретируются буквально. Сортировка фиксирована: дата создания и UUID по
убыванию. Удалённые пользователи не попадают в каталог; ссылка при совпадении
email может открыть их карточку. Имеющийся статус SUSPENDED отображается отдельно.

Пустой набор ролей допустим. Новая форма предлагает STUDENT. Управляются ADMIN,
CONTENT_EDITOR, INSTRUCTOR, STUDENT; существующие нестандартные роли сохраняются.
Панель не создаёт роли и не удаляет пользователей.

## Создание и приглашение

Создание атомарно сохраняет учётную запись PENDING, роли, событие, хеш токена и
ключ идемпотентности. Администратор не задаёт пароль. Отправка SMTP выполняется
после транзакции. Ошибка отправки возвращает созданного пользователя с FAILED;
повтор обращается к приглашению этой учётной записи. SENT означает успешный
ответ почтового адаптера, а не подтверждённую доставку или прочтение.

`requestId` — UUID. Повтор создания тем же администратором с тем же UUID и данными
возвращает существующий результат без второго пользователя или письма. Изменённые
данные с тем же ключом дают `409 REQUEST_REUSED`. При потере ответа форма сохраняет
поля и ключ для безопасного повтора. Совпадение email даёт `409 EMAIL_EXISTS` с
`existingUserId`, который используется для перехода к существующей карточке.

Приглашение действует 24 часа. Повтор доступен не чаще раза в минуту и заменяет
предыдущий секрет. Использованные ключи повторной отправки сохраняются: даже
запоздалый повтор старого запроса не выпускает новую ссылку. Если процесс
прервался во время отправки, SENDING через минуту читается как UNKNOWN;
администратор может повторить отправку. Письмо от старого поколения не меняет
состояние нового. Принятие и повтор сериализованы; подтверждённая активация не
перезаписывается поздним результатом SMTP.

Токен хранится только в виде SHA-256 digest; административные ответы его не
содержат. В письме он передаётся во фрагменте URL `#token=…`; страница немедленно
убирает фрагмент из адресной строки и не выводит секрет. Пароль должен содержать
8–72 символа и занимать не более 72 байт UTF-8 из-за BCrypt. Принятие атомарно
устанавливает пароль, подтверждает email, активирует пользователя и погашает
токен. Истёкший, заменённый или уже принятый токен возвращает одинаковую ошибку.

Для настоящей отправки нужны `MAIL_ENABLED=true`, параметры SMTP и `APP_BASE_URL`,
указывающий на внешний адрес frontend без завершающего `/`. При выключенной почте
существующий mock-адаптер сохраняет письмо в памяти и не отправляет его в сеть.

## Роли, блокировки и история

Изменение ролей и доступа требует актуальной `version`. Триггеры PostgreSQL
увеличивают версию также при изменениях через старые role API и workflow.
`409 VERSION_CONFLICT` сохраняет локальный выбор, блокирует сохранение и предлагает
перечитать данные. Потерянный ответ также требует перечитать результат. Перезаписи
поверх неизвестной версии нет. Снятие ADMIN имеет отдельное подтверждение.

Действующий администратор имеет ADMIN, подтверждённый email и статус ACTIVE либо
LOCKED. Временная защита входа не исключает его из числа действующих
администраторов. Общая транзакционная advisory-блокировка сериализует снятие ролей,
удаление через старый API, блокировки и активацию. Проверка всего набора
пользователей запрещает оставить систему без такого администратора, включая
конкурирующие запросы. Себя можно менять при наличии другого администратора.

Административная блокировка разрешена для ACTIVE/LOCKED. Она сохраняет временную
блокировку. Снятие временной блокировки очищает срок и счётчик, сохраняя BLOCKED.
Снятие административной возвращает LOCKED, если временная ещё действует.
Неактивированным пользователям не предлагается ручная активация или блокировка.
Панель не обещает мгновенного отзыва уже выданных JWT и сессий других сервисов;
новые административные запросы проверяют актуальное состояние БД.

Каждое событие содержит отдельную цель и снимок имени автора на момент действия.
Позднее переименование автора не переписывает историю. Системные назначения ролей
подписаны как системные действия. События старого API назначения ролей также
попадают в историю. События, существовавшие до V13, не реконструируются.
Даты интерфейса показываются в Europe/Moscow; технические идентификаторы и секреты
в истории не выводятся.

## Миграция и локальная проверка

V13 добавляет версию пользователя, CONTENT_EDITOR, таблицы приглашений,
идемпотентности и событий. Перед применением к существующей БД нужно разрешить
дубли нормализованного email. Миграция намеренно не объединяет людей автоматически:

```sql
SELECT lower(btrim(email)), count(*) FROM users
GROUP BY lower(btrim(email)) HAVING count(*) > 1;
```

Полный локальный прогон из корня, с Java 21, Node.js 24, Docker Compose и Chromium:

```sh
python3 scripts/user-admin-e2e.py
```

Он собирает сервисы и frontend, выполняет lint/typecheck, создаёт отдельный Compose
проект с tmpfs PostgreSQL и SMTP-приёмником только для `example.test`. Затем проходят
регрессионные проверки редактора и диалогов и сценарии админ-панели. Порты публикуются
на loopback, существующие базы и сервисы не используются. Собственные контейнеры,
образы и сеть удаляются даже при ошибке. Логи, скриншоты и traces сохраняются в
`reports/user-admin-e2e/<run>/`; они содержат только синтетические данные.

Проверки backend отдельно:

```sh
./gradlew :user-service:check securityContract
python3 -m unittest discover -s scripts -p test_editor_e2e.py -v
```

`UserAdminIT` проверяет настоящую PostgreSQL/Flyway, отказы по ролям и устаревшему
JWT, потерянный ответ создания, ошибки писем, повтор старых запросов, истечение
приглашения, гонку принятия, конфликты версий, старые role/delete API, конкурентное
снятие ADMIN, независимые блокировки и снимок автора. Браузерный сценарий проходит
реальный SMTP, установку пароля и вход нового пользователя, фильтры и пагинацию,
ошибки и повторы, обе темы 1440/390/320, текст 200%, клавиатуру и ограничения BFF.
Проверка клавиатуры не заменяет отдельное тестирование экранным диктором.
